# 安装与升级

模版与实例是两份独立的仓库：模版只装机制，实例装真实业务。这份文档讲清
`bin/opc install` / `bin/opc upgrade` 做了什么、文件归谁、以及旧实例怎么迁过来。

## 两个仓库

| | 模版 | 实例 |
|---|---|---|
| 位置 | `~/Projects/opc-template` | `~/Projects/<实例目录>`（路径由 owner 定） |
| 版本库 | 公开仓库 `Woods30/opc-template` | 本地 git，**无远端** |
| 装什么 | `template/` 下的运行载荷 | 真实业务、实例配置、机制副本 |
| 谁能写 | owner | owner + 角色（按 scope） |

模版仓库根目录的 `.opc-template-repo` 是标记。实例安装器检测到它就拒绝执行——
模版不能变成实例。

## 载荷分三层

模版里的载荷不是一坨，按归属分三层。三层的管理方式完全不同，升级时各走各的路。

| 层 | 装什么 | 归谁 | 升级行为 |
|---|---|---|---|
| **机制** | `scripts/`、`tools/`、`LICENSE` | 模版 | 整目录覆盖；本地改过就拒绝升级 |
| **起始材料** | 根 `AGENTS.md`、`agents/<角色>/`、`skills/<名字>/`、业务种子 | owner（装一次就归 owner） | 按基线比对，逐份决定更新 / 保留 / 跳过 / 补入 |
| **实例自有** | `knowledge/`、`roles.json`、`channels.json`、`.opc/` | 实例 | 永不覆盖；配置只按键合并 |

分层的理由：机制装错会坏，owner 不该改；起始材料是 owner 的工作台，模版只能「补」；
实例自有是业务事实，模版根本不该碰。三层混在一起时，owner 想改一句角色职责就会撞上
机制指纹，升级要么拒绝要么覆盖。

## 安装

```sh
bin/opc install <实例目录> [前缀] [--dry-run] [--no-input] [--template <路径>]
```

顺序：

1. 解析模版源（见「缓存与自动拉取」）；
2. 校验目标：目录不存在或为空；不是模版仓库；不覆盖已有实例；
3. 复制机制：`scripts/`、`tools/`、`LICENSE`；
4. 写配置：`roles.json`、`channels.json`；
5. 装起始材料：`AGENTS.md`、`agents/`、`skills/` 与业务种子，并写
   `.opc/starters.json`（每份材料的相对路径与 SHA-256 基线）；
6. 写 `.opc/instance.json`（前缀、模版来源、install 时间）与
   `.opc/mechanism.json`（每个机制文件的 SHA-256）；
7. `git init`；
8. 跑实例的 `scripts/opc-install.sh --no-input`：生成启动器、角色设置、
   `knowledge/` 目录与名册；
9. 做第一次提交：只包含模版生成的内容；
10. 安装全局 UI（布局与 mod），写注册表，把 `bin/opc` 链到 `~/.local/bin/opc`。

第 8 步在提交之前：安装器生成的启动器、权限设置与名册也属于「模版生成的内容」，
要在第一次提交里带上，实例仓库才是完整快照。

前缀默认取目录名 slug。目标目录**不要含空格**，否则 `hc` 模板的 `command`
会被拆开。

## 升级

```sh
opc upgrade [实例目录] [--dry-run] [--force-mechanism] [--force-ui] [--yes]
opc upgrade --all
```

默认升级当前目录；`--all` 遍历注册表 `~/.config/opc/instances.json`。

升级顺序：

1. 读 `.opc/instance.json` 与 `.opc/mechanism.json`；
2. **校验机制指纹**：记录里的文件被改过或被删掉 → 打印 diff，拒绝升级；
   确认放弃本地改动后加 `--force-mechanism`；
3. 规划角色单文件迁移与起始材料更新，并检查必需的起始材料是否缺失
   （根 `AGENTS.md`、启用角色的入口文件）；缺失直接失败；
4. `--dry-run` 在这里打印全部动作：机制覆盖项、起始材料的更新 / 新增 / 跳过 /
   保留 / 冻结、角色迁移；
5. 执行角色迁移（见「角色单文件迁移」）；
6. 覆盖机制目录与文件；清单外的新文件（如 `opc-role.sh add` 生成的角色模板）保留；
7. 合并配置：`roles.json` 按 `name`、`channels.json` 按 `id`，只增不改，
   新条目默认 `enabled: false`；
8. 重写 `.opc/instance.json` 与 `.opc/mechanism.json`（机制哈希按新版本重算）；
9. 按 `.opc/starters.json` 的基线更新起始材料（见下），并重写基线；
10. 删掉模版已移除、且不再属于起始材料的机制文件；
11. 跑实例安装器：hc 模板、权限设置与技能索引同步更新；
12. 安装全局 UI（`--all` 只在最后装一次）；
13. 做一个限定 pathspec 的提交；
14. 更新注册表。

`knowledge/` 永远不动。

### 指纹代替三方合并

实例里的机制文件是模版的副本，不允许本地定制。`.opc/mechanism.json` 记录每个
文件的 SHA-256（换行统一成 LF 后计算），升级前逐个比对：

- 全部一致：整目录覆盖；
- 有不一致：列出文件并打印模版与实例的 diff，拒绝；
- 新增文件：直接写入；
- 模版删了文件：实例里对应删除。

没有基线快照、没有 `mark`、没有冲突目录。指纹只管机制文件：起始材料归基线管，
实例自有归 owner 管，都不参与指纹比对。

### 起始材料按基线更新

机制之外的材料装一次就归 owner：`AGENTS.md`、`agents/`、`skills/` 与业务种子。
`.opc/starters.json` 记下每份材料的相对路径与 SHA-256 基线，升级时逐个比对：

| 状态 | 升级行为 |
|---|---|
| 存在，哈希等于基线 | 用模版版本刷新，基线跟着更新 |
| 存在，哈希不同 | 视为 owner 改过：保留、告警，不覆盖 |
| 不在实例里，基线里记过 | 视为 owner 删过：不复活 |
| 不在实例里，基线里没有 | 模版新增：补入 |
| 实例里有、模版没有 | owner 自加：永不触碰 |

另有一种情况：实例里有这个文件，但基线里没有记录它（老实例或 owner 自己放的）。
角色与技能材料（`AGENTS.md`、`agents/`、`skills/`）遇到这种情况，内容与模版一致就
收编进基线，从此跟随模版更新；不一致就保留并记成 pinned，以后升级不再动它。

业务种子只补不覆盖：实例里已经有就留着（业务事实归 owner），owner 删掉的不再补；
模版新增的种子只在目标缺失时补入。种子不跟随模版更新——它记的是业务事实。

技能目录以目录为单位冻结：目录里任一已记录文件被改、或出现 owner 新增的文件，
整个技能跳过更新并告警——免得 `SKILL.md` 与脚本出现半新半旧的版本。角色目录
按文件管理：`agents/<角色>/AGENTS.md` 与目录里的参考文件互不影响。

起始材料一律**不删实例里的文件**：模版移除了某份材料时只在输出里提示，由 owner
自己决定要不要删。

两种情况直接失败：根 `AGENTS.md` 缺失、启用角色的入口文件缺失。停用角色不受这个
限制，它的入口文件被删了也不补回。`knowledge/` 下的业务内容永远不动。

### 角色材料与 hc 模板

角色材料是目录：`agents/<角色>/AGENTS.md` 是入口，纯 Markdown，不带 hc
frontmatter，目录里还可以放角色专属参考文件。角色元数据都在 `roles.json`：
一句话描述、启用状态、CLI、权限模式、可写子树、选中的技能。

安装器按这三段拼出 hc 模板（写在全局模板目录，名为 `<前缀>-<角色>.md`）：

1. **frontmatter**：`name` 是 `<前缀>-<角色>`，`description` 取自
   `roles.json`，`command` 指向生成的启动器 `.opc/run/<角色>.sh`；
2. **正文**：角色 `AGENTS.md` 的内容，`{{PREFIX}}` 占位符在这一步替换；
3. **技能索引**：只列 `roles.json` 的 `skills` 里选中、且
   `skills/<名字>/SKILL.md` 确实存在的技能，每条给出名字、一句话用途与路径；
   一个都没选中时不生成这一节。

实例里的 `agents/<角色>/AGENTS.md` **不被安装器改写**：它属于 owner，
改完重跑安装脚本，hc 模板会跟着更新。启用的角色缺入口文件时安装与升级都直接
失败；停用的角色不生成 hc 模板，并清理掉它以前的模板文件。

### 技能库

技能统一放在实例根 `skills/<名字>/SKILL.md`，装实例时**整库复制**模版的技能库，
角色在 `roles.json` 的 `skills` 里选用。技能 frontmatter 必须有 `name`（与目录名
一致）与 `description`（单行）。

- 选中的技能文件缺失、frontmatter 不合法或指向实例外时，索引跳过该条并告警，
  不阻断角色启动——别的角色仍要能跑起来。
- 根级技能**不链接**到 `.claude/skills/` 或 `.agents/skills/`：CLI 原生的技能发现
  走自己的目录，OPC 靠 hc 模板里的索引加按需读取，不依赖 CLI 自动触发。
- `approvedSkills` 与 `skills` 是两回事：前者放行 CLI 原生技能的调用权限
  （生成精确的 `Skill(<名字>)` 规则），后者只决定索引里列哪些。
- 模版新增的技能在实例里不存在时补入；实例里已有同名技能且内容与模版不同时，
  保留实例版本并告警。

## 全局 UI

布局与看板 mod 只安装一份，放在 `$HERDR_APP_HOME`（默认
`~/.config/herdr-app/`）：

| 来源 | 安装名 |
|---|---|
| `template/layouts/opc.json` | `layouts/opc.json` + `layouts/opc.svg` |
| `template/layouts/focus.json` | `layouts/opc-focus.json` |
| `template/layouts/grid.json` | `layouts/opc-grid.json` |
| `template/layouts/monitor.json` | `layouts/opc-monitor.json` |
| `template/mods/opc-dashboard/` | `mods/opc-dashboard/` |
| `template/mods/opc-tabs/` | `mods/opc-tabs/` |

- 名称固定，不带实例前缀，不含 `{{...}}` 占位。
- 安装前备份到 `~/.config/opc/backups/<时间戳>/`。
- 哈希记录在 `~/.config/opc/ui.json`；已记录的本地修改需要 `--force-ui`。
- 单一全局 UI 的后果：升级任意实例都会更新所有实例共用的 UI；重启
  `herdr-app` 生效。
- `opc-tabs` 每 2 秒读当前 space 的 `<folder>/.opc/instance.json`，只有
  `kind === "opc-instance"` 才显示「看板」按钮；非 OPC 目录与远端 space 隐藏。

## 缓存与自动拉取

首次 `opc install` 会把模版 clone 到 `~/.local/share/opc/template`，并把
`bin/opc` 链到 `~/.local/bin/opc`（`~/.local/bin` 不在 PATH 时打印提示）。

| 场景 | 行为 |
|---|---|
| 普通安装/升级 | 先 `fetch`，缓存快进到 `origin/main`（非快进则中止），再 `re-exec` 缓存里的 `bin/opc` |
| `OPC_TEMPLATE` 或 `--template` 指向开发副本 | 直接用工作区代码，**不自动拉取** |
| `--no-pull` | 跳过拉取，使用缓存当前内容 |
| fetch 失败（离线/远端不可达） | 告警，用缓存继续 |
| 缓存损坏或非快进 | 中止，提示删除缓存重装 |
| 刷新后继续执行 | 设置 `OPC_CACHE_READY=1` 后 `re-exec`，避免新旧代码混跑 |

远端地址解析顺序：`OPC_TEMPLATE_REMOTE` 环境变量 → 仓库根的
`.opc-template-remote` → 开发副本的 `git origin` → 公开 HTTPS 地址。

## 注册表

`~/.config/opc/instances.json`：

```json
{
  "instances": [
    {
      "path": "<实例绝对路径>",
      "prefix": "acme",
      "installedAt": "2026-11-06T12:00:00+08:00",
      "updatedAt": "2026-11-06T12:00:00+08:00",
      "template": { "path": "...", "commit": "..." }
    }
  ]
}
```

`opc ls` 列出实例；目录缺失会标出来。`opc upgrade --all` 只升级注册表里的实例。
注册表只记元数据，不感知业务内容。

## 旧实例迁移

检测到下列任一项即进入一次性迁移：

- `layouts/`、`mods/`、`seeds/`、`tools/tests/`
- `sync-policy.json`、`template.lock.json`
- `.opc/sync-*`
- `scripts/opc-sync.sh`、`scripts/opc-new.sh`
- `.claude/commands/opc-init.md`（基线与实例一致时）

流程：

1. 读 `.opc/instance.json` 取前缀与模版来源；缺失则拒绝。
2. 用 `.opc/sync-base/`（其次实例 git 首次添加该文件的提交）作为基线，
   比对机制文件；有本地改动则打印 diff 并拒绝。
3. 删除路径若有未提交改动，拒绝并列出。
4. `--dry-run` 打印全部动作：实例内删除项、机制新增/更新、配置新增、骨架、
   全局删除项、将创建的单个提交。
5. 确认（交互或 `--yes`）后：备份到 `~/.config/opc/backups/`，删除旧副本，
   复制新机制，合并配置，物化缺失骨架，写新 `.opc/*.json`。
6. 做一个限定 pathspec 的提交。
7. 清理 `$HERDR_APP_HOME/{layouts,mods}` 里所有 `<前缀>-*` 旧产物，安装全局 UI，
   跑实例安装器，写注册表。

`knowledge/` 永不触碰。

### 角色单文件迁移

角色目录化之前，角色简报是 `agents/` 下的单文件（`agents/opc-<角色>.md`），
职责描述写在文件自己的 frontmatter 里。只要 `roles.json` 里还有角色条目的
`template` 指向 `agents/` 下的单文件，`opc upgrade` 就顺手把它迁到角色目录：

1. 正文原样写进 `agents/<角色>/AGENTS.md`（`{{PREFIX}}` 占位符保留）。
2. frontmatter 的 `description` 写进 `roles.json` 的角色条目；没有就用角色名
   生成占位描述并告警。
3. 角色条目的 `template` 指向 `agents/<角色>/AGENTS.md`，`skills` 置空——迁移
   不套模版的默认技能，升级不悄悄改变角色的行为。
4. 旧简报连同原始 frontmatter 备份到 `.opc/backups/agents/`，原文件移除。
5. 迁出来的文件记进 `.opc/starters.json`：旧指纹（`.opc/mechanism.json`）里
   的哈希与文件对不上，说明 owner 改过，记成 pinned，之后升级不再覆盖；对得上
   就按普通起始材料处理，跟随模版更新。

迁移是幂等的：重复升级不会再建目录、再拷内容或覆盖已迁移的文件。`--dry-run`
逐项打印迁移动作，正式执行前可以先审一遍。迁移只提交自己动过的路径，
`knowledge/` 永不触碰。

两个边界：旧简报是指向实例外的软链接时不读它的内容——读进来就等于把实例外的
文件抄进角色提示词，只改元数据并告警；`agents/<角色>/` 已经存在时不覆盖，
把它认成 owner 的内容并记成 pinned。

## 护栏

- 模版仓库守卫：在模版目录跑实例安装器直接退出。
- 目标目录非空、含非法前缀、已是实例：`install` 拒绝。
- 机制文件本地改过：`upgrade` 拒绝，`--force-mechanism` 才覆盖。
- 全局 UI 已记录哈希且被改过：拒绝，`--force-ui` 才覆盖。
- 旧结构与未提交改动：拒绝，先提交或 stash。
- 提交只包含本次动作的 pathspec，不带上工作区无关脏文件。
- 所有写入先落到临时文件，再原子替换，避免中途失败留下半个文件。

## 排障

| 现象 | 处理 |
|---|---|
| `opc: command not found` | `~/.local/bin` 不在 PATH；加进 PATH 或直接用 `<模版>/bin/opc` |
| `opc upgrade` 报机制文件被本地改过 | 看 diff，确认放弃本地改动后 `--force-mechanism` |
| `opc upgrade` 报缓存非快进/损坏 | 删除 `~/.local/share/opc/template` 后重试，或 `--no-pull` |
| `opc upgrade` 报「起始材料缺失」 | 根 `AGENTS.md` 或启用角色的 `agents/<角色>/AGENTS.md` 不见了；从 git 里恢复，或该角色确实不用了就先在 `roles.json` 里停用 |
| 升级输出「已本地修改，已保留」 | owner 改过起始材料，模版不会覆盖它；要跟模版同步就手动对齐，或删掉本地版本让升级重新写入 |
| 升级输出「技能冻结（整目录跳过更新）」 | 技能目录里有文件被改过或有 owner 新增的文件，整个技能保持你的版本；要跟模版同步就自行合并后删掉多余文件再升级 |
| 升级输出「模版已移除该起始材料（实例保留）」 | 模版不再提供这份材料，实例里的文件留着不删；要删自己动手 |
| 实例 `scripts/opc-lint.sh` 报结构问题 | 实例侧只查结构：角色路径、入口文件、技能引用与 frontmatter、根 `AGENTS.md`、hc 模板 |
| 升级后角色行为没变 | 提示词与权限在安装器里生成；`scripts/opc-down.sh && scripts/opc-up.sh` |
| 升级后看板没更新 | 全局 UI 只有一份；重启 `herdr-app` |
| 非 OPC space 没有「看板」按钮 | 预期行为；space 的 folder 要以实例根为准 |
| 迁移后旧前缀 UI 还在 | 确认迁移提交成功；清理步骤在提交之后，失败会保留备份 |
