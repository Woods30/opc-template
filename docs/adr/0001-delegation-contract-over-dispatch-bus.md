# 用委派契约替代编排者中心的派工总线

原先的协作协议里，编排者（gm）是所有消息的中转站：派工写进收件箱 →
`hc send` 唤醒对方 → 对方完成后 `hc send` 回编排者 → 编排者核对产出并把
那一行改成完成态 → 再派下一轮。每一环的记账都要花掉编排者一次完整的
agent 回合，而角色规约里「空闲时主动巡检三个收件箱」又让编排者自己把自己
叫醒，于是形成自持循环。

改为**委派契约**：任务带上边界（做到哪算完、完成后交给谁），完成方直接通知
下游，不再经编排者中转；编排者只在三种情况下被唤醒——owner 直接下指令、
角色请求裁决、任务链到达审批点。终端本身仍用 HC 调度（`hc send` 唤醒角色
会话），变的是**契约**而不是传输。

## 考虑过的替代方案

- **保留编排者中心 + 加回合预算**：只治标，回路仍在，只是被卡住；角色与
  编排者之间的每一次交接仍是一次无产出的编排者回合。
- **用 HC 的父子进程语义（`hc run` + `hc wait --children`）替代**：
  这是 HC 原生的 SubAgent 模式，但它要求被委派方是一次性会话。owner 明确
  选择四个角色 tab 各自跑**常驻会话**（tab 稳定、owner 随时可看），因此
  一次性父子语义不适用；委派契约在常驻会话上照样成立。

## 后果

- 编排者不再巡接收件箱，不再替别人搬运事实；它的上下文增长慢得多。
- 角色之间的反馈（growth → content）走链边直送，不必绕编排者。
- 每个角色 tab 里的会话上下文仍然累积——这是被明确接受的代价，靠
  「记忆注入只读该读的」压住增量。
