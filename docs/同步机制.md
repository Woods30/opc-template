# 同步机制

模版与实例是两份独立的仓库，靠 `scripts/opc-sync.sh` 连接。这份文档讲清
「哪个文件归谁、同步时怎么处理冲突」。

## 两个仓库

| | 模版 | 实例 |
|---|---|---|
| 位置 | `~/Projects/opc-template` | `~/Documents/OPC` |
| 版本库 | 公开仓库 `Woods30/opc-template` | 本地 git，**无远端** |
| 装什么 | 机制、规约、占位骨架 | 真实业务、实例配置、机制副本 |
| 谁能写 | owner | owner + 角色（按 scope） |

模版仓库根目录的 `.opc-template-repo` 是标记。`opc-install.sh` 与
`opc-sync.sh` 检测到它就拒绝执行——模版不能变成实例。

## 五档文件分类

分类表在模版仓库的 `sync-policy.json`，是同步与自检共同的唯一权威。

| mode | 语义 | 同步行为 |
|---|---|---|
| `managed` | 机制与规约 | 实例没改过就覆盖；改过而模版也改了走三路合并，冲突则不动 |
| `merge` | 结构化配置 | 按 key 并集，只增不改；模版新增的条目并入实例并默认停用 |
| `seed` | 说明文档 | 实例缺失时物化一次，之后归实例所有 |
| `seeds` | 占位骨架源 | 实例持有快照（覆盖式拷贝），快照同时是业务文件的合并基线 |
| `local` | 实例自有 | 永不触碰 |
| `template-only` | 模版独占 | 不进实例 |

### 为什么骨架要单独放 `seeds/`

如果占位骨架继续待在 `knowledge/business/品牌口径.md`，它就同时是
「模版的模板」和「实例的真实业务」——同一个路径两种身份，模版一改就撞车，
最后只能退化成「打印 diff 让人工合并」。搬到 `seeds/` 之后：

- 模版仓库里**根本没有 `knowledge/` 目录**，模板不含业务成了目录级的事实；
- 实例的骨架有基线可比对，能分清「业务没动过 → 自动升级」与
  「业务改过了 → 只报 diff，绝不硬写」。

## 判定表

设 `B` = 基线（上次同步下来的模版原文，存在 `.opc/sync-base/`）、
`T` = 模版当前内容、`L` = 实例当前内容。

| 条件 | 动作 |
|---|---|
| 模板有、实例无 | 复制（`add`） |
| `L == T` | 无事可做（`identical`） |
| `L == B` 且 `T != B` | 覆盖，模版赢（`update`） |
| `L != B` 且 `T == B` | 保留本地，提示用 `mark` 固化（`local-modified`） |
| `L != B` 且 `T != B` | 三路合并；冲突则**不动业务文件**，产物写 `.opc/sync-conflicts/` |
| 没有 `B` | 判不出本地是否改过，报 `unknown`——不是「没有差异」 |
| 已 `mark` pin | 不动（`pinned`） |
| 模版删了文件 | 不删；报 `orphan`，`--prune` 才删（且要求本地没改过） |

### 基线从哪来

`opc-new.sh` 建实例时会把模版当时的内容抄一份到 `.opc/sync-base/`，那就是基线。
有了基线，模版后续改了机制文件，`check` 才会报 `update`、`pull` 才会覆盖实例；
没有基线就只剩「判不出本地改没改过」这一句，模版更新传不进实例。

老实例（或基线被清掉的实例）跑一次 `scripts/opc-sync.sh baseline --from <模版>` 补上：
内容取自实例 git 里这些文件**第一次被加入**的那次提交——也就是建实例时的快照。
它只补缺失的基线，不覆盖已有基线，也不动任何业务文件。

## 种子骨架的升级

```
模版改了 seeds/business/品牌口径.md
        │
        ▼
实例 knowledge/business/品牌口径.md 不存在 ──→ 直接物化
        │ 存在
        ▼
内容 == 基线快照？ ──是──→ 自动升级（骨架改进零人工）
        │ 否（业务已经写了）
        ▼
报 seed-diff，只给 diff；要吸收新版骨架就跑
scripts/opc-sync.sh seeds --merge knowledge/business/品牌口径.md
        │
        ├─ 合并干净 → 写回
        └─ 有冲突 → 产出 .merge 文件，人工改
```

冲突时基线**不推进**，下次同步继续在同一个基线上合。

## 护栏

- 模版仓库守卫：在模版目录跑 `install` / `sync` 直接退出 2。
- 工作区脏：只有**将被覆盖的路径**脏了才拒绝同步；业务文件没提交不挡路。
- 角色在跑：`hc ls` 查本前缀终端，只提示「提示词类改动需重启才生效」，不自动重启。
- 同步后自动重跑 `scripts/opc-install.sh`，否则角色简报与权限还是旧的。
- 同步脚本自身本轮不覆盖（`deferred`）——bash 脚本执行中被覆盖会读到乱码。
  新版先落到 `.opc/sync-stage/`，下次运行启动时自我替换并重新执行。
- 策略里的路径必须在仓库根内：绝对路径、`..` 成分、符号链接成分一律拒绝，
  校验不过直接退出 2（`sync-policy.json` 是数据文件，不能当可信输入）。
- 本地改过的文件默认保留。确认要以模版版本为准时点名采用：
  `scripts/opc-sync.sh pull --accept-template <路径>`（可多次给，`all` 表示全部）。

## 日常命令

```sh
scripts/opc-sync.sh check            # 看这次有什么变化
scripts/opc-sync.sh pull             # 拉更新
scripts/opc-sync.sh baseline         # 固化基线快照（老实例接入时用）
scripts/opc-sync.sh seeds            # 看骨架差异
scripts/opc-sync.sh mark <路径>       # 固化本地定制
scripts/opc-sync.sh status           # 摘要
```

退出码：`0` 成功/无差异；`1` 有差异或失败；`2` 用法/环境错；`3` 有冲突
（业务文件未被改动）。
